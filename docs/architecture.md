# 아키텍처와 설계 판단

이 문서는 "무엇을 만들었는가"보다 **"왜 그렇게 만들었는가"** 를 적습니다.
확장하거나 뜯어고칠 때 필요한 것은 결국 이쪽입니다.

---

## 계층

```
  L5  CLI / 워크플로        pf check | solve | calibrate | run
  L4  시나리오 · 리포트      what-if YAML, 관리기준 판정, 단일 HTML 리포트
  L3  데이터 · 보정          태그맵, 5분 평균 정렬, 파라미터 추정, 식별성 진단
  L2  물리 컴포넌트          Duct, Fan, Mixer, ToolGroupSource, WetScrubber, Stack
  L1  조립 · 해석            연결 → 방정식 조립 → 구조 해석 → 블록 뉴턴
  L0  심볼릭 · 단위          식 그래프, 해석적 미분, 코드 생성, 차원 검사
```

**L0 ~ L1 은 도메인을 전혀 모릅니다.** NOx 도, 스크러버도, 공기도 모릅니다. 냉동기든
압축공기든 새 계통은 L2 에 컴포넌트를 추가하는 것으로 끝납니다.

## 판단 1. 무인과(acausal) 모델링

컴포넌트는 입출력 방향을 고정하지 않고 **잔차 형태의 방정식**만 선언합니다.

```python
def equations(self, s):
    a, b = s.port("a"), s.port("b")
    return [a.mdot + b.mdot,                                # = 0 이 되도록 푼다
            a.p - b.p - s.dp, ...]
```

무엇이 미지수인지는 계통을 연결한 뒤 구조 해석이 정합니다.

**왜.** 유틸리티 계통의 질문은 방향이 계속 바뀝니다. 설계할 때는 "이 유량을 흘리려면
팬이 몇 mmAq 필요한가", 운전할 때는 "이 팬으로 얼마나 흐르는가", 진단할 때는 "차압이
이렇게 나오려면 저항이 얼마여야 하는가". 인과 모델이면 세 개의 코드를 따로 짜야
하지만, 무인과 모델은 하나면 됩니다.

**대가.** 방정식 개수를 사용자가 직접 맞춰야 합니다. 그래서 구조 해석(판단 3)이
반드시 같이 있어야 합니다.

## 판단 2. 포트는 across / through / stream

| 종류 | 연결 시 | 예 |
|---|---|---|
| across | 서로 **같다** | 압력 |
| through | 합이 **0** | 질량유량 (컴포넌트로 들어가는 방향이 +) |
| stream | 유동 따라 **전달** | 온도, 화학종 질량분율 |

Modelica 의 stream connector 처럼 완전 일반화하지 않고 **1:1 연결로 제한**했습니다.
합류/분기는 `Mixer` / `Splitter` 를 명시적으로 두어야 합니다.

**왜.** stream connector 의 일반 해법(`inStream` 연산자)은 구현이 복잡하고, 무엇보다
오류 메시지가 사람이 읽을 수 없게 됩니다. 유틸리티 배관망은 합류 지점이 도면에
명확히 찍혀 있으므로, 명시적 Mixer 가 모델을 더 정직하게 만들고 진단도 친절해집니다.
같은 포트를 두 번 연결하면 이렇게 말해 줍니다:

```
포트 'HDR.in1' 가 이미 'DCT_DRY.b' 에 연결되어 있습니다.
합류/분기는 Mixer/Splitter 컴포넌트를 쓰세요.
```

### 방정식 개수 맞추기

1:1 연결 하나는 미지수 12개(포트 2개 × 6변수)를 만들고 방정식 6개를 줍니다.
따라서 **포트 하나당 컴포넌트가 평균 3개의 방정식**을 대야 합니다.
내부 변수는 정의식이 1:1로 따라붙으므로 개수에 중립입니다.

| 컴포넌트 | 포트 | 내부변수 | 필요 | 실제 | 차이 |
|---|---|---|---|---|---|
| Duct | 2 | 2 | 8 | 8 | 0 |
| Fan | 2 | 3 | 9 | 9 | 0 |
| Mixer(N) | N+1 | 0 | 3N+3 | N+5 | −2N+2 |
| ToolGroupSource | 1 | 1 | 4 | 6 | **+2** |
| WetScrubber | 2 | 5 | 11 | 11 | 0 |
| Stack | 1 | 8 | 11 | 9 | **−2** |

경계 컴포넌트가 잉여/부족을 만들고 서로 상쇄합니다. 유량원(+2)은 유량·온도·조성을
정하고 압력은 계통에 맡깁니다. 대기 경계(−2)는 압력만 정하고 나머지는 받습니다.
직접 세어볼 필요는 없습니다 — `pf check` 가 해 줍니다.

## 판단 3. 풀기 전에 구조부터 본다

`core/structural.py` 는 희소 구조만 보고 다음을 판정합니다.

1. **최대 매칭** (증대경로법): 방정식 ↔ 미지수 짝짓기
2. **Dulmage-Mendelsohn**: 짝 없는 쪽에서 교대경로로 부족/과결정 블록을 찾아 이름으로 보고
3. **BLT** (Tarjan SCC): 정방이면 풀이 순서와 블록 크기 산출

**왜 이게 사용성을 좌우하는가.** 물리 모델을 짜다 보면 방정식이 하나 모자라거나
중복되는 일이 다반사입니다. 그냥 뉴턴법에 던지면 "특이 행렬" 한 줄이 전부입니다.
여기서는 `SCR.m_evap, SCR.b.T 를 결정할 식이 부족합니다` 라고 말해 줍니다.

**성능에도 직결됩니다.** 174×174 을 한 번에 푸는 대신 1×1 스칼라 14개 + 160×160
한 덩어리로 쪼갭니다. 예제에서 냉시동 뉴턴 반복이 전체 9회로 끝납니다.

## 판단 4. 심볼릭 엔진을 직접 만든다

사내 PC 에 CasADi/JAX 설치를 장담할 수 없습니다. 그런데 수치미분으로는 강성 계통이
수렴하지 않습니다. 그래서 `core/symbolic.py` 에 최소 심볼릭 코어를 두었습니다.

* **해시콘싱**: 구조가 같은 부분식은 같은 객체. 공통 부분식 제거가 공짜로 됩니다.
* **스마트 생성자**: `x+0`, `x*1`, `x/x` 를 생성 시점에 정리해 그래프가 부풀지 않습니다.
  단 **차원을 가진 상수는 약분하지 않습니다** (`T / const(1.0, K)` 를 지우면 차원
  검사가 무력화됩니다).
* **교환법칙 정규화**: `a+1` 과 `1+a` 가 같은 노드가 되도록 인자 순서를 고정합니다.
* **해석적 미분 + 코드 생성**: 파이썬 소스를 만들어 `exec` 합니다. 호출 오버헤드가
  거의 없습니다.
* **희소성**: 구조적으로 등장하는 (식, 미지수) 쌍만 미분합니다. 예제에서 25,614 개가
  아니라 **499 개**만 생성됩니다.

### 차원 검사

모든 심볼이 7차원 벡터(m, kg, s, K, mol, A, cd)를 갖고, 조립 시 방정식의 동차성을
검사합니다. 수치 리터럴(`0.5`)은 차원이 `None` 이라 주변에 맞춰지고, 차원이 필요한
상수는 `S.const(9.80665, ACCEL)` 처럼 명시합니다.

```
[SCR eq[8]] 차원 오류
  덧셈의 차원이 다릅니다: [m^2*kg/s^2] + [m^2/s^2]
```

## 판단 5. 스케일링된 블록 뉴턴법

한 블록 안에 압력(1e5 Pa)과 질량분율(1e-4)이 섞이면 야코비안 조건수가 1e9 를 넘습니다.
그래서 매 반복마다 **열 스케일**(변수 크기)과 **행 스케일**(|J|·c 행합)로 균등화한 뒤
풉니다. 수렴 판정도 절대값이 아니라 이 스케일 대비 상대값으로 합니다.

블록이 50을 넘으면 희소 LU(구조는 한 번만 만들고 값만 교체), 아래면 dense 를 씁니다.
경계 제약은 스텝 배율 제한으로 지키고, Armijo 선탐색으로 전역 수렴을 돕습니다.

### 초기값 전파

물리 모델은 초기값이 나쁘면 발산합니다. 각 컴포넌트가 `initial_guess()` 로 자기 출구
상태를 대충이라도 계산하면, 위상 순서를 따라 하류로 전파되어 계통 전체가 합리적인
출발점에서 시작합니다. 사용자가 손으로 초기값을 찍을 일이 없습니다.

## 판단 6. 모든 기지량은 파라미터

시간에 따라 변하는 입력(가동율, 외기온도)도 별도 개념을 두지 않고 **파라미터 값을
매 시점 갈아 끼웁니다**. 5분 평균 데이터를 시점별 정상상태로 연속해서 푸는 방식
(quasi-steady)이며, 직전 해를 다음 스텝 초기값으로 씁니다.

`der()` 로 상태변수를 선언하면 과도 해석도 됩니다 (음함수 오일러로 이산화해 같은
뉴턴 엔진으로 풉니다). 배기 계통은 체류시간이 수십 초라 5분 평균에서는 준정상이
타당하지만, 덕트 열용량이나 스크러버 순환수 탱크를 넣을 때를 위해 엔진에 넣어
두었습니다.

## 판단 7. 보정값은 코드가 아니라 데이터

모델 코드는 **설계값**을 들고, 현장에 맞춘 값은 `params_fitted.yaml` 로 따로 둡니다.
라인별·호기별로 파일만 갈아끼우면 같은 모델이 여러 계통에 붙습니다.

마찬가지로 현장 태그 이름은 코드가 아니라 `tagmap.yaml` 에만 존재합니다.
**모델 코드에 사내 태그가 들어가지 않습니다.**

## 판단 8. 식별성을 항상 같이 본다

잔차가 작다고 파라미터가 결정된 것은 아닙니다. 굴뚝 농도는 (발생량)×(1−η) 로만
들어오므로 발생량과 최대효율은 **곱으로만** 결정됩니다. 개별 값은 아무 데나 가도
잔차가 같습니다.

그래서 보정 결과에는 항상 표준오차와 상관계수를 붙이고, 상대표준오차 50% 초과나
상관계수 0.95 초과를 경고합니다. 이때 **정칙화 항은 제외하고 데이터 항만으로**
공분산을 계산합니다 — 정칙화는 야코비안에 단위행렬을 더하는 것과 같아서, 그대로
두면 상관이 인위적으로 낮아져 "식별된 것처럼" 보입니다.

식별되지 않은 파라미터는 둘 중 하나로 처리합니다.

* 설계값에 **고정**하고 나머지만 보정한다 (예제에서 `SCR.eta_max` 를 그렇게 했습니다)
* 둘을 분리할 수 있는 **운전 구간 데이터를 확보**한다 (순환수량을 일부러 바꿔 보는 등)
