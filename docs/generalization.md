# 범용화: 지배방정식을 직접 선언하고, 후보 중에서 고르기

"사용자가 후보 물리 지배방정식을 말하면 최적 모델을 골라 준다" — 가능합니다.
다만 **무엇을 후보로 둘 수 있고 무엇은 둘 수 없는지**가 먼저 명확해야 합니다.

---

## 1. 절대 후보가 아닌 것 vs 후보로 두는 것

| | 예 | 후보? |
|---|---|---|
| **보존법칙** | 질량, 운동량, 에너지, 화학종 | **아니오. 공리다.** |
| **상태방정식** | 이상기체, 증기압 | 아니오 (매질이 정해지면 결정) |
| **구성방정식(closure)** | 마찰 상관식, 물질전달 상관식, 성능곡선, 열전달 상관식 | **예. 여기가 후보의 자리.** |
| **경계조건 구조** | 유량 고정 vs 압력 구동 | 예 (단, 이건 모델링 판단에 가깝다) |

보존법칙을 후보로 돌리는 순간 **외삽 보증이 사라집니다.** 물리모델을 쓰는 유일한
이유가 "학습 데이터 밖에서도 질량과 에너지는 보존된다"인데, 그걸 데이터로 정하면
결국 형태만 물리학처럼 생긴 회귀모형입니다.

> 데이터에서 방정식 자체를 발견하는 방법(SINDy 계열 희소회귀)은 깨끗한 시뮬레이션
> 데이터에서는 동작하지만, 현장 노이즈에서는 무너지고 **보존법칙을 위반하는 식**을
> 내놓습니다. 우리가 원하는 것은 그게 아닙니다.

그래서 이 툴의 구조는 이렇습니다:

```
구조(보존법칙)  = 고정          <- 외삽 보증의 근거
구성방정식      = 후보 중 선택   <- 데이터가 고른다
파라미터        = 보정           <- 데이터가 맞춘다
```

## 2. 지배방정식을 YAML 에 직접 쓴다

파이썬을 건드리지 않고 컴포넌트를 만듭니다. 손으로 짠 컴포넌트와 **완전히 같은
식 그래프**가 나오므로 해석적 미분·차원 검사·구조 해석이 그대로 적용됩니다.

```yaml
ports:
  a: {kind: gas, role: in}
  b: {kind: gas, role: out}
params:
  K:  {value: 30, unit: "1/m4", tunable: true}
  UA: {value: 5000, unit: W/K, tunable: true}
vars:
  dp:  {unit: Pa, start: 100}
  rho: {unit: kg/m3, start: 1.15, lo: 0.05, hi: 10}
equations:
  mass:     "a.mdot + b.mdot = 0"
  state:    "rho = density(a)"
  friction: "dp = K * signed_pow(a.mdot, 2) / rho"
  momentum: "a.p - b.p = dp"
  energy:   "abs(a.mdot) * cp(a) * (a.T - b.T) = UA * ((a.T + b.T)/2 - 298.15[K])"
outputs:
  dp_mmAq: {expr: "dp", unit: mmAq}
```

쓸 수 있는 것:

| | |
|---|---|
| 연산자 | `+ - * / ^`, 괄호, 단항 `-` (`^` 는 우결합) |
| 수학 함수 | `exp log ln sqrt sin cos tanh abs sq max min signed_pow` |
| 물성 함수 | `density(a) enthalpy(a) cp(a) molar_mass(a) Qn(mdot, a) p_sat(T) humidity(rh,T,p)` |
| 상태변수 | `der(T_wall)` — 과도 해석 시 자동 이산화 |
| 포트 변수 | `a.mdot`, `a.p`, `a.T`, `a.w_NOx` … |
| 단위 리터럴 | `150[mmAq]`, `273.15[K]`, `4186[J/(kg*K)]` |

**단위 리터럴이 중요합니다.** 맨 숫자는 무차원으로 취급되므로, 차원이 있는 상수는
`[...]` 로 단위를 달아야 차원 검사가 삽니다.

### 방정식에 이름을 붙인다

`equations` 가 dict 인 것은 의도적입니다. 이름이 있으면

* 진단 메시지가 `SCR.closure_eta` 처럼 뜹니다 (`SCR eq[3]` 보다 훨씬 빠릅니다)
* **이름 하나만 골라 교체**할 수 있습니다 — 다음 절의 토대입니다

### 새 도메인도 파이썬 없이

포트 종류는 `gas` / `liquid` / `thermal` 이 기본 제공되고, 레지스트리에 추가할 수
있습니다. 테스트(`tests/test_generic.py`)에 액체 배관 계통을 YAML 만으로 만들어
해석해와 대조하는 예가 있습니다 — 파이썬 0줄입니다.

## 3. 구성방정식 후보 비교

`extends` 로 기본 정의를 상속하고 **방정식 한 줄만 갈아끼웁니다.**

```yaml
# scrubber_langmuir.yaml
extends: scrubber_base.yaml
params:
  k_LG: {value: 3.5e-3, unit: "1", lo: 1.0e-6, hi: 1.0, tunable: true}
equations:
  closure_eta: "eta = eta_max * LG / (k_LG + LG)"
```

보존법칙 10개는 원본 그대로 남고 구성방정식 1개만 바뀝니다. 쓰이지 않게 된
파라미터(`ntu_a` 등)는 모델에서 **자동으로 사라집니다** — 식에 등장하지 않는
심볼은 미지수/파라미터 목록에 들어가지 않기 때문입니다.

```bash
pf select examples/nox_stack/selection.yaml
```

## 4. 무엇을 기준으로 고르는가

네 가지를 **같이** 봅니다. 하나로 줄이면 반드시 속습니다.

### ① 외삽 구간 오차 (1차 기준)

학습에 쓰지 않은 **운전영역**에서의 RMSE. 무작위 k-fold 가 아니라 **운전구간으로
자른 분할**이어야 합니다. 무작위로 나누면 학습과 검증이 같은 분포가 되어 외삽
능력을 전혀 재지 못합니다.

학습 구간 적합도는 기준이 될 수 없습니다. 파라미터를 늘리면 언제나 좋아집니다.

### ② AICc

학습 적합도 + 파라미터 수 벌점. 복잡도가 값을 하는지 봅니다.
**보조 지표입니다** — 학습 구간 기반이라 외삽 능력을 직접 재지 못합니다.

### ③ 식별성

파라미터가 실제로 결정되었는가. 상관계수 0.98 초과나 상대표준오차 200% 초과면
예측이 맞더라도 파라미터를 물리적으로 해석하면 안 됩니다.

### ④ 물리적 타당성

보정값이 허용 경계에 붙었는가. 붙었다면 대개 **모델 형태 자체가 틀렸다**는
신호입니다.

### 그리고 오컴의 면도날

외삽 오차가 5% 이내로 비슷하면 **파라미터가 적은 쪽**을 택합니다. 툴이 이 경우를
따로 짚어 줍니다.

---

### 통계적 유의성은 기준이 아니다

5분 데이터 한 달이면 검증 표본이 수천 개입니다. 그러면 **아무리 작은 차이도
통계적으로 유의미**해집니다. 실제 예제에서 측정한 값:

| 비교 | 평균 절대오차 차이 | 표준오차 | 차이/표준오차 | 계측 불확도 대비 |
|---|---|---|---|---|
| 1위 vs 2위 | 0.033 mg/Sm³ | 0.0011 | **31.6** | 1.1% |
| 1위 vs 4위 | 0.168 mg/Sm³ | 0.0049 | **33.9** | 5.6% |

차이/표준오차가 30을 넘으니 통계적으로는 "압도적으로 유의미"합니다. 그런데 그
차이의 크기는 계측 불확도(σ=3.0 mg/Sm³)의 1~6% 입니다. **아무 의미 없습니다.**

그래서 툴의 1차 판정은 **계측 불확도 대비 크기**입니다. 최선과 최악의 차이가
σ의 20% 미만이면 "고를 수 없다"고 말합니다. 통계적 유의성은 참고로만 표시하고,
표본이 커서 유의하게 나왔을 뿐이라는 점을 함께 적습니다.

(자기상관 보정은 여전히 합니다. 5분 잔차는 자기상관이 있어 유효 표본수가
6,158 → 약 2,500~2,900 으로 줄었습니다. 보정하지 않으면 더 심하게 과신합니다.)

### 순위가 흔들리면 그 순위는 노이즈다

같은 예제를 보정 표본 수만 바꿔(80행 → 25행) 다시 돌렸더니 **순위가 완전히
뒤집혔습니다.**

| 보정 표본 | 1위 | 2위 | 3위 | 4위 |
|---|---|---|---|---|
| 80행 | langmuir (2.524) | ntu_power (2.549) | ntu_power_T (2.552) | constant (2.565) |
| 25행 | constant (3.604) | ntu_power (3.640) | ntu_power_T (3.649) | langmuir (3.786) |

1위와 4위가 자리를 맞바꿨습니다. 순위가 보정 설정에 이 정도로 민감하면 그 순위는
물리가 아니라 수치 잡음입니다. **후보 비교 결과를 보고할 때는 설정을 바꿔 한 번 더
돌려 보세요.**

## 5. 후보를 반드시 하나는 "너무 단순한 것"으로

비교군에 **하한선 모델**(null model)을 꼭 넣으세요. 스크러버라면 "제거효율 =
상수"입니다. 이것보다 나은지 확인하지 않으면 복잡한 상관식이 값을 하는지 알 수
없습니다.

반대쪽으로 **의도적 과다 매개변수화** 후보도 하나 넣으면, 툴이 그걸 잡아내는지
확인할 수 있습니다 (학습 잔차는 같거나 줄지만 식별성이 무너지고 AICc 가 벌점을
먹어야 정상입니다).

## 6. LLM/에이전트의 자리

역할이 명확히 갈립니다.

| 하는 일 | 누가 |
|---|---|
| 자연어 요구 → **후보 집합 제안** ("NOx 습식흡수면 이런 상관식들이 후보다") | LLM |
| 후보를 YAML 구성방정식으로 초안 작성 | LLM |
| **구조 검증** (차원 동차성, 방정식 개수, 보존법칙 잔차) | 툴 |
| **보정 + 외삽 검증 + 식별성 진단** | 툴 |
| **선택** | 툴 (수치적 근거) |
| 결과 해석과 설명 | LLM |

**LLM 이 절대 하면 안 되는 것**: 숫자를 만들어내는 것, 어느 후보가 최적인지
판단하는 것. 제안은 LLM, 판정은 물리 엔진입니다.

이 분업이 지켜지면 "AI 가 모델을 만들어 준다"가 환각 없이 성립합니다. LLM 이
틀린 상관식을 제안해도 차원 검사와 구조 해석에서 걸리고, 그럴듯하지만 데이터와
맞지 않는 형태를 제안해도 외삽 검증에서 떨어집니다.

## 7. 한계 (정직하게)

* 후보 집합 **밖에** 정답이 있으면 이 비교는 가장 덜 틀린 것을 고를 뿐입니다.
  모든 후보의 외삽 오차가 크다면 형태를 더 찾아야 한다는 뜻입니다.
* 후보 수 × 파라미터 수가 늘면 계산 시간이 선형 이상으로 늡니다. 구성방정식
  여러 개를 동시에 후보로 돌리면 조합이 폭발하므로, **한 번에 하나씩** 고정하며
  단계적으로 좁히는 편이 낫습니다.
* 선택은 **주어진 데이터가 덮는 운전영역**에 대한 판정입니다. 데이터에 변동이 없는
  변수(예: 거의 일정한 입구 온도)에 대한 의존성은 어떤 방법으로도 고를 수 없습니다.
