
윈도우에서는 `run_pforecast.bat` 더블클릭 — 설치(처음 한 번, 오프라인 묶음 지원)와 실행을
한 번에 합니다. [`windows.md`](windows.md)

브라우저가 뜨고 `http://127.0.0.1:8765` 에 붙습니다. **의존성은 표준 라이브러리뿐**
입니다 — FastAPI 도 Streamlit 도 쓰지 않습니다. 사내 잠긴 PC 에서 한 줄로 떠야 하고,
프레임워크가 하나라도 막히면 도구 전체가 멈추기 때문입니다. 프런트엔드도 CDN 을
쓰지 않아 외부 요청이 **0건** 입니다.

## 시작 화면 — 계통이 무엇이든 같은 흐름

어떤 계통(배기·냉동·압축공기·공조 …)이든 순서는 같습니다: **데이터**(CSV)와 **계통
모델**(지배방정식)을 연결하고, 과거로 **검증**한 뒤, 계획을 넣어 **미래를 예측**합니다.
화면에 특정 계통의 용어는 없고, 계통 지식은 모델 파일(컴포넌트)에만 있습니다.

| 시작 카드 | 가는 곳 |
|---|---|
| **데이터로 예측 모델 만들기** | 1~6단계 (아래). 모델이 없으면 ML 만으로도 |
| **계통 모델 만들기·고치기** | 모델 만들기 — 컴포넌트를 골라 연결 (코드 없음) — [`builder.md`](builder.md) |
| **운전 조건 바꿔 보기** | 모델 구조 → 시나리오 (손잡이를 움직이면 바로 다시 풂) |

아래에 **최근 프로젝트**가 있습니다. 검증이나 미래 예측을 실행할 때마다 설정과 결과가
`projects/<이름>.yaml`(+ `.result.json`)에 자동 저장되고, ‘열기’를 누르면 데이터·변수·기간·
모델 연결·구성방정식 선택·계획·결과가 그대로 돌아옵니다. 위쪽 오른쪽의 프로젝트 이름을 누르면
이름을 바꿔 저장합니다. 같은 파일을 CLI 가 읽습니다 (`pf project run`, `pf forecast`).

## 간편 예측 1~6단계 — CSV 하나로 물리모델 + ML 비교, 그리고 미래 예측

위쪽 1~6 단계를 차례로 누르면 됩니다. 앞 단계를 마치기 전에는 뒤 단계가 잠겨 있고,
앞 단계에서 예측할 값이나 기간을 바꾸면 뒤 단계가 다시 잠깁니다 (이전 선택이 조용히
따라붙지 않게).

| 단계 | 하는 일 |
|---|---|
| **1. 데이터** | CSV 를 끌어다 놓거나 클릭해서 고릅니다. 파일은 작업 폴더의 `uploads/` 에만 저장되고 (`.gitignore` 로 커밋 차단), 이 PC 밖으로 나가지 않습니다. 현장 파일(CP949, 여러 줄 헤더, 상태 문자열, `+09:00`·`Z` 같은 시간대가 붙은 시각)을 그대로 읽고 **무엇을 고쳤는지 전부** 보여줍니다. 태그가 작업 폴더의 보정 설정(YAML)과 60% 이상 겹치면 그 설정의 타깃·입력·모델 연결을 미리 채웁니다. |
| **2. 변수** | 표에서 **y(예측할 값)** 하나를 ◉, **x(입력)** 를 ☑. 컬럼마다 추이 미니차트·단위·범위·결측·이상 배지가 있고, 이름을 누르면 시계열과 정리한 점이 뜹니다. 저장된 설정에서 결과값(관측)으로 쓰던 컬럼을 x 로 고르면 **‘결과값 — 누수 주의’** 배지가 붙습니다. |
| **3. 기간** | y 시계열 위를 **끌어서** 학습 기간·예측 기간을 고르거나 날짜를 입력합니다. 빠른 선택: 앞 60% 학습 → 나머지 예측 / 마지막 30일 / 마지막 7일. |
| **4. 모델·실행** | ‘물리모델 + ML 비교’(권장) 또는 ‘ML 만’. ① 계통 모델(파일이 하나면 자동 선택) → ② **컬럼 ↔ 모델 연결은 자동 추천으로 채워 둡니다** — 확인만 하고 틀린 줄만 고르면 됩니다 (아래) → ③ 보조 계측값(선택) → ④ 고급(보정 파라미터·구성방정식, 기본값이면 충분). 관리기준을 넣으면 초과 시간 적중·오경보를 셉니다. 구성방정식 후보 비교는 [`closures.md`](closures.md). |
| **5. 검증 결과** | 모델별 RMSE 타일, 실측 vs 예측 시계열(학습/예측 구간 배경, 범례로 켜고 끄기), 예측 vs 실측 산점도, **외삽 행 vs 범위 안 행** RMSE 막대, 비교 표, 보정된 파라미터 + 식별성 경고, **모델 설명**(아래), 예측 결과 CSV 내려받기, CLI 로 다시 돌릴 설정 YAML. |
| **6. 미래 예측** | 과거 전체(기본)로 학습하고, **계획**(입력의 앞으로 값 — 최근 패턴을 조정해 만들거나 CSV 로 올림)을 예측합니다. 설비 상태 변동 폭, 학습 범위 밖 음영, 관리기준 초과 예상 시간. [`forecast.md`](forecast.md) |

### 컬럼 ↔ 모델 연결 — 추천이 채우고, 사람은 확인만

모델의 입력 후보는 수십 개(예제 NOx 모델: 입력 48개, 출력 60개)라 목록에서 직접 고르기 어렵습니다.
그래서 코드가 **CSV 의 태그 이름·설명 행·단위**와 **모델 변수의 이름·설명·단위**를 비교해 점수를
매기고, 확실한 것은 미리 채웁니다 (LLM 없음, `easy.suggest_mapping`).

* 이름은 계통과 무관한 일반 계측 용어(온도·유량·압력·차압·가동률·대수·회전수·외기·전력 …)와
  태그 조각(`DRY`, `SCR`)으로 맞춥니다. **뜻이 하나는 맞아야** 후보가 됩니다 — 위치(컴포넌트 이름)만
  같은 것은 후보가 아닙니다 (DRY 가동률 ≠ DRY 장비 대수).
* 단위 차원이 다르면 크게 깎습니다. 인버터 주파수(Hz)를 정격 대비 비율로 받는 모델이면 단위 1 +
  배율 1/60 을 같이 채웁니다.
* 한 모델 입력에는 한 컬럼만. 모든 곳이 같은 값을 쓰는 입력(외기온도)은 ‘전체 N곳’으로.
* 보조 계측값은 모델이 **‘현장 계측값’으로 선언한 것만** 자동으로 켭니다. 나머지 추천은 ‘추천
  있음’으로만 보입니다 (보정에 넣을 관측은 결과를 바꾸므로 사람이 켭니다).
* 선택 상자 맨 위 **★ 추천** 이 점수 순 후보입니다. 줄마다 ✓/⚠ 가 붙고, 단위가 안 맞는 줄은 이유와
  단위·배율 칸이 열립니다. **★ 추천대로 다시 채우기** 로 되돌릴 수 있습니다.

현장형 더미(`nox_field`)의 컬럼으로 저장된 설정 없이 돌리면, 입력 8개 · 예측할 값 · 보조 계측값 4개가
사람이 맞춘 `tagmap.yaml` 과 **13개 모두 같게** 채워졌습니다 (인버터 배율 포함). 냉수 플랜트 모델에
가상의 컬럼 6개(총 전력·냉방 부하·습구온도·냉수 공급온도·COP·냉각수 온도)를 넣었을 때도 6개 모두
맞았습니다 (`tests/test_mapping.py`). 시간대(`+09:00`)가 붙은 같은 데이터를 빈 작업 폴더에 올려 추천 그대로
실행하니 외삽 행 RMSE 가 물리모델 3.25 / ML 다항 11.79 / ML 부스팅 19.39 mg/Nm3 로, 저장된 설정으로 돌린
아래 결과와 같았습니다.

### 모델 설명 — 무엇으로 어떻게 예측했나

결과 화면 아래쪽 카드에서 모델마다 탭을 눌러 봅니다.

* **물리모델**: 방정식 수 = 미지수 수, 계통 흐름(배기원 → 굴뚝), 입력 컬럼이 들어가는
  식, 컴포넌트별 지배방정식. 식마다 종류(보존법칙·상태·정의·구성방정식·경계조건)가 붙고,
  보정한 파라미터는 식 안에서 강조되며 설계값 → 보정값이 같이 나옵니다. 보정 파라미터는
  구성방정식에만 있습니다 (`tests/test_explain.py` 가 검사). 풀이 방법과 보정 목적함수도 적습니다.
* **ML 다항·부스팅**: 알고리즘 식, 학습된 모델에서 읽은 설정(항 수, 트리 수, 학습률, 조기 종료
  등), 쓴 입력, 학습 범위 밖에서 어떻게 행동하는지. 학습 동안 고정이었던 입력을 따로 표시합니다.

식은 컴포넌트의 `LAWS` 에서 옵니다 (`docs/adding_components.md` 9번). YAML 선언형
컴포넌트는 선언한 식이 그대로 나옵니다.

### 누수는 화면이 먼저 막고, 서버가 한 번 더 거절합니다

* 예측 시작은 **학습 끝 다음 날 + 간격(기본 1일, 최소 1일)** 보다 앞으로 갈 수 없습니다.
  날짜를 앞으로 당기면 자동으로 되돌리고 이유를 알려줍니다. API 를 직접 불러도
  `400` 으로 거절합니다 (`tests/test_easy.py`).
* 기간을 바꿀 때마다 **누수·외삽 검사**가 다시 돕니다: 미래인가, 간격은 며칠인가, 학습·예측
  행 수, 예측 기간 중 **학습 운전영역 밖(외삽) 행의 비율**, 입력별 학습 범위 vs 예측 범위 막대.
  외삽이 50% 미만이면 “ML 도 잘 맞히는 조건이라 차이가 작게 나올 수 있다”고 경고합니다.
* 값 정제(교정 창·스파이크)는 **학습·간격·예측 구간을 따로** 합니다.
* 물리모델과 ML 은 **같은 학습 행, 같은 입력**으로 학습합니다. ML 에는 다항(2차)과
  그래디언트 부스팅이 들어갑니다.
* 결과의 1순위 지표는 **예측 기간 중 외삽 행의 RMSE** 입니다. 범위 안 행은 따로 적습니다.
* 학습 동안 한 번도 변하지 않았는데 예측 기간에 바뀐 입력(증설 전 장비 대수 등)은
  결과 맨 위에 적습니다. ML 은 그 변화의 효과를 배울 방법이 없습니다.

### 실제로 돌려 본 결과

`examples/nox_field/data/field_raw.csv`(현장형 더미, 5분 × 8개월)를 업로드하고 저장된 설정이
채워 준 그대로, 빠른 선택 ‘앞 60% 학습’(학습 2025-01-01~05-26, 간격 1일, 예측 05-28~08-31)으로
실행한 값입니다. 예측 기간의 90% 가 학습 운전영역 밖이었고, 건식 장비 대수
(`F2_FAB_DRY_EQP_CNT`)는 학습 동안 고정이었다가 예측 기간에 바뀌었습니다.

| 모델 | 외삽 행 RMSE (23,797행) | 범위 안 행 RMSE (2,753행) | 예측 기간 전체 |
|---|---|---|---|
| 물리모델 | **3.25** mg/Nm3 | 4.19 | 3.36 |
| ML 다항(2차) | 11.79 | 3.33 | 11.21 |
| ML 부스팅 | 19.39 | 6.97 | 18.50 |

실행 시간은 두 번 돌려 175초·176초(보정 150행 + 예측 26,550행)였습니다. 학습 범위 안에서는 ML 다항이
물리모델보다 낮고(3.33 vs 4.19), 차이는 외삽 행에서 드러납니다. ‘ML 만’ 모드는 5분 데이터
한 달 기준 1초 남짓입니다.

## 고급 화면

위쪽 ‘고급’ 탭은 데이터 주도 분석(XAI), 물리모델 구조, 실시간 시나리오입니다.

### 1. 데이터 — 단위 지정이 전부입니다

작업 폴더의 CSV 를 훑어 목록으로 보여주고, 고르면 프로파일링합니다.

* **현장 파일을 있는 그대로 읽습니다** — CP949(한글 엑셀), 태그/설명/단위 여러 줄 헤더,
  `2025-01-01 오후 3:05` 날짜, `Bad`·`Comm Fail`·`#N/A` 상태 문자열, 천 단위 콤마,
  이어 붙인 파일의 중간 헤더·겹친 구간·뒤바뀐 순서. 엑셀에서 손질할 필요가 없습니다.
* **데이터 정리 내역** 카드 — 파일에서 고친 것과 값에서 뺀 것을 전부 적습니다.
  조용히 고치지 않습니다.
* 값 이상 탐지: 분석계 **정기 교정 창**(매일 같은 시각의 영점/스팬), **고착**(마지막 값
  유지), **스파이크**(단선 999.9 등), 1시간 갱신 집계값, 장기 결측. 값이 정확히 0 으로
  유지되는 구간(펌프 정지)은 설비 정지로 보고 지우지 않습니다.
* 컬럼 이름을 누르면 시계열이 뜨고, **결측 처리한 점이 빨간 점**으로 원래 값 그대로
  찍힙니다. 무엇을 왜 뺐는지 눈으로 확인하세요.
* 컬럼별 범위·결측·상수·중복 판정, 이상 배지
* **파일에 단위 행이 있으면 그것을**, 없으면 태그 이름에서 단위를 추론 — 노란 칸은
  신뢰도가 낮으니 확인하라는 뜻
* 타깃 컬럼, **입력**(미래에도 미리 아는 값: 생산계획의 가동율, 기상예보의 외기,
  설정값), 제어 가능 변수를 체크. 입력을 체크하면 분석에서 **미래 예측 성능을 따로**
  잽니다 — 같은 시각에 측정되는 결과값(굴뚝 유량·압력)을 쓴 '현재값 추정'과 섞지 않습니다.

단위를 왜 이렇게 강조하느냐면, **단위가 있어야 차원 해석(L2)과 보존식 탐지(L3)가
열리기 때문**입니다. 단위 없이도 ML 은 돌지만 그건 그냥 ML 입니다.

추론 규칙은 국내 팹 태그 관례를 따릅니다. `_TEMP`→degC, `_NOX`→mg/Nm3,
`_UTIL`→%, `_HZ`→Hz, `_DP`/`_SP`→mmAq 등. 유량과 압력은 이름만으로 못 정하므로
**값의 크기**로 후보를 고르고 확인을 요청합니다 (예: 대푯값 1.4 → kg/s, 13,000 → Nm3/h).

### 2. 분석 — 사다리를 어디까지 올라갔나

`pf analyze` 와 같은 내용을 화면으로 봅니다. 요약 타일, 먼저 읽을 문장, 사다리
5단계 상태, 자동 발견한 보존식, **묶음 기준 영향인자**, 교차검증 예측 추종.

누수 방지 규칙이 기본으로 걸려 있습니다: 학습/검증은 **시간순 + 하루 간격**, 교차검증은
**앞 구간으로만 학습**(전진), 지연은 과거 쪽만, 값 정제는 학습·검증 **따로**. 미래 예측
타일은 **학습 운전영역 밖(외삽) 행**의 오차를 보여 줍니다 — 차이는 거기서만 드러납니다.

영향인자를 묶음 기준으로 먼저 보여주는 이유는 `docs/data_driven.md` 에 있습니다 —
개별 순열 중요도는 상관된 변수 사이에서 순위가 뒤집힙니다.

### 3. 물리모델 — 풀기 전에 구조부터

모델을 고르면 조립하고 구조를 검사합니다. 방정식/미지수 개수, BLT 블록 구조,
야코비안 non-zero 개수, 컴포넌트 목록.

### 4. 시나리오 — 손잡이를 끌면 그 자리에서 다시 풉니다

**이 화면이 물리 모델을 쓰는 이유를 체감시키는 곳입니다.**

정상상태 1회가 4~15 ms 라 슬라이더가 즉각 반응합니다. 과거 데이터에 한 번도 없던
조건(증설, 설비 교체, 극한 기상)을 끌어봐도 답이 나옵니다 — ML 대리모델이
원리적으로 못 하는 일입니다.

* 손잡이는 모델이 `DRIVERS` 로 선언합니다 (없으면 자동 추출)
* 관리기준(`LIMITS`)이 걸린 출력은 KPI 타일에서 초과 시 빨갛게 표시
* 민감도 스윕: 손잡이 하나를 끝에서 끝까지 훑어 곡선과 관리기준선을 같이 그림
* 스윕 캡션이 **변화폭을 %로** 알려줍니다. 세로축 눈금이 좁으면 기울기가 커 보이는데,
  실제로는 영향이 없는 경우를 구분하기 위해서입니다

## 운전 손잡이 선언

모델이 직접 선언하는 편이 훨씬 낫습니다. 자동 추출은 대기압·기준밀도 같은 상수까지
손잡이로 끌어옵니다.

```python
# model.py
DRIVERS = [
    {"key": "util",    "label": "가동율",        "unit": "%",     "lo": 20,  "hi": 130},
    {"key": "n_tools", "label": "장비 대수",      "mode": "scale", "lo": 0.5, "hi": 2.0},
    {"key": "T_amb",   "label": "외기온도",       "unit": "degC",  "lo": -10, "hi": 40},
]
LIMITS = {
    "STK.C_dry": {"max": 100.0, "label": "사내 관리기준"},
    "SRC_DRY.q_per_tool": {"min": 3.0, "label": "후드 포집 한계"},
}
```

YAML 모델도 똑같이 `drivers:` / `limits:` 로 선언합니다.

`key` 는 파라미터 이름의 **마지막 조각**입니다. `SRC_DRY.util`, `SRC_CVD.util` …
네 개가 손잡이 하나로 묶입니다. 팹 계통은 같은 종류 설비가 여러 대 붙는 구조라
이 규칙이 잘 맞습니다.

`mode: scale` 은 절대값이 아니라 **설계 대비 배율**입니다. 장비 대수처럼 군마다
값이 다른 것에 씁니다.

## API

앱은 얇은 JSON API 위에 올라가 있습니다. 다른 도구에 붙일 때 그대로 쓰면 됩니다.

| 엔드포인트 | 하는 일 |
|---|---|
| `GET /api/workspace` | 작업 폴더의 CSV·모델 목록 |
| `POST /api/upload?name=` | CSV 원본 바이트를 `uploads/` 에 저장 (최대 300 MB, 같은 이름·다른 내용이면 `_1`) |
| `POST /api/easy/presets` | 이 CSV 의 태그와 맞는 저장된 보정 설정 |
| `POST /api/easy/catalog` | 모델의 입력 후보·관측 후보·보정 파라미터(+타깃 민감도) |
| `POST /api/easy/check` | 기간·입력 검사 (누수·간격·외삽·입력별 범위, 연결 단위 검사) |
| `POST /api/easy/run` | 물리모델 + ML 실행 (비동기, `job` 반환). 누수 기간은 `400`. `closures` 로 고른 구성방정식 |
| `POST /api/easy/closures` | 구성방정식 후보 비교 (비동기, 학습 기간만). 슬롯별 추천과 근거 |
| `POST /api/profile` | 수집·정리 내역 + 값 이상 + 프로파일링 + 단위 |
| `POST /api/preview` | 컬럼 시계열 (다운샘플) + 결측 처리한 점 |
| `POST /api/analyze` | 분석 사다리 실행 (비동기, `job` 반환) |
| `GET /api/job?id=` | 작업 상태 폴링 |
| `POST /api/model/meta` | 구조 진단 + 손잡이 + 출력 + 관리기준 |
| `POST /api/model/solve` | 정상상태 1회 (4~15 ms) |
| `POST /api/model/sweep` | 손잡이 하나를 훑으며 연속 풀이 |
| `POST /api/forecast/make` · `check` · `run`, `GET /api/forecast/plans` | 미래 예측 — [`forecast.md`](forecast.md) |
| `GET /api/project/list`, `POST /api/project/save` · `load` | 프로젝트 저장·열기 (`load` 는 없어진 데이터·모델 경로를 `missing` 으로 알려줌) |
| `GET /api/builder/palette`, `POST /api/builder/load` · `check` · `save` | 모델 만들기 — [`builder.md`](builder.md) |

긴 작업만 스레드로 돌리고 나머지는 요청 안에서 바로 처리합니다. 컴파일된 모델은
캐시하고 직전 해를 warm start 로 재사용합니다.

## 알아둘 것

* **보안**: `127.0.0.1` 에만 바인딩합니다. 작업 폴더 밖 경로는 거부합니다 (`%2e%2e` 같은
  인코딩된 경로도 풀어서 검사합니다).
* 올린 CSV 는 `uploads/`, 검증 결과는 `out/easy/`, 미래 예측 결과는 `out/forecast/`, 계획은
  `plans/`, 프로젝트는 `projects/`, 만든 모델은 `models/` 에 남습니다. 전부 커밋되지 않습니다
  (태그 이름·설계값·현장 값이 들어가므로).
* `plans/` 의 CSV 는 학습 데이터 목록에 뜨지 않습니다 (계획 목록에만).
* 작업 폴더를 훑을 때 `.venv`·`venv`·`site-packages`·`wheels` 같은 폴더는 들어가지 않습니다
  (저장소 안에 가상환경을 만들어도 목록이 느려지거나 남의 YAML 이 모델로 잡히지 않게).
* **데이터는 서버로 나가지 않습니다.** 전부 로컬에서 처리됩니다.
* 10MB(7만 행 × 25 태그) CSV 의 첫 읽기·정리는 약 3초, 이후엔 캐시에서 0.2초입니다.
  파일이 바뀌면(수정 시각·크기) 다시 읽습니다.
* `_` 로 시작하는 폴더(예: 더미 데이터의 정답지 `_answer/`)는 목록에 뜨지 않습니다.
* 모델 파일을 고치고 나면 물리모델 화면의 **다시 불러오기**를 누르세요.
